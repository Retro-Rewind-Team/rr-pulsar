# Contributing to Retro Rewind Pulsar

The rules in this file only apply to the rr-pulsar codebase **NOT** the other related Retro Rewind repositories. 
By submitting a PR, you agree that your contribution is licensed under this repository’s license with no additional conditions, and that you have the right to submit it.

Members of the direct development team or select contributors selected by pack management may be exempt from the rules in this file for any reason. The licensing terms apply to all contributions, including the team’s.


## Important note for security-relevant contributions or reports

Please do not publicly report vulnerabilities that could be exploited in the live version of rr-pulsar. Instead, please join our Discord at https://discord.gg/RetroRewind and open a Discord ticket at #create-ticket or contact 4ab via DM on Discord for responsible disclosure.

This also applies to vuln fixes. Please don't open a public PR for an exploitable issue. Contact us first so we can implement and ship the fix before the details are public.

## Before you start

Please read the contributing guidelines and familiarize yourself with them before contributing, as contributing to rr-pulsar can be a bit different to what you are used to from other open source projects.

If you contribute to Retro Rewind Pulsar, we expect that you have read the guidelines and will act accordingly.

Retro Rewind is a passion project run by volunteers, and final decisions are made by a small core team. Contributions will be hand-picked and may be edited or fully reworked to fit the contribution team's vision.

Our developers code as a hobby, not a job, so please keep this in mind when working together with them.

## How we use GitHub

We use GitHub mostly as a tool and less of a collaboration platform. That's why issues and pull requests may not always be handled promptly or at all.

Please do not consider missing responses as a judgment/decision about your code or us intentionally ignoring you. Much of our discussion happens in private team channels.


## Adding New Features

Before you start adding new features, ensure that you understand:
1. **No guarantees:** Your feature is not guaranteed to actually be added to Retro Rewind. Using the "Feature Submission Application" issue template can be a great way to find out if the team is interested in your work, before you actually start the work.
2. **Functionality is Desired:** The feature should actually be something improving Retro Rewind. Think a bug fix or a highly requested feature.
3. **Useful PRs:** Your PR should consist of re-usable and extendable code, it should be useful for future work or other developers.
4. **Feature PR:** Submitting a PR does not give you full exclusive control over the feature, and we may reimplement any way we see fit if your PR does not meet the standards or feature request changes.
5. **Useful Comments:** You must comment your code to explain its purpose and reasoning. **Write these comments yourself**, as AI-generated comments fail to explain the decisions behind the code.


## Pull Request Guidelines

Pull requests should explain what they do, what they edit and *why* the change is needed.

### PR Title

Make sure your PR title starts with one of the following (or something similar):

- `fix:`
- `feature:`

Examples:

- `fix: removed goku from the game (again)`
- `feature: added new character in the game (goku)`

### PR Description

Please add these sections to your PR description:

- Start with a high-level explanation of what the PR does.
- Provide testing instructions and where to find your feature.
- What you changed. Not line by line, but in general.

### AI-generated Content

If your PR uses AI-generated code, include an **AI Usage** section in the PR description. You must specify which parts were generated by AI.

Explain what AI tools you used and how you used them during development, any changes you made to their output and how you reviewed and tested.

AI-generated content other than code is strictly forbidden in any contributions to Retro Rewind. This also includes documentation of your PR, PR titles and descriptions, images, and other assets. 

The allowance for AI-generated code does not extend to the text explaining that code. Your PR description must be written by you and you should be able to explain what you changed without the help of an LLM.

Using AI doesn't lower the bar for contributions, you must understand, build and test everything you submit.

## Crediting

### When credit is given

Credit will be given if your code was used or we consider our code heavily inspired by your code and/or ideas.

### How credit is given

The only credit we can guarantee is credit given in the update changelogs posted on Discord. We usually use your GitHub name for this.

Additionally, update changelogs are usually copy-pasted to ZPL's YouTube channel community and the Wiiki. If you are credited on the Discord but not on the Wiiki, you are free to add this credit, according to the Wiiki's formatting convention, in the version history yourself.

Providing credit in any other format (such as in commit messages, as co-author on the commit, in-game etc) **is not planned** and cannot be guaranteed, even if requested.

In most cases, non-trivial code contributions make you eligible for the Contributor badge on Retro WFC, the Code Contributor rank on Discord and a mention on our website. In order to get it, you have to request it in a Discord ticket on the Retro Rewind Discord. Requests through any other means may not be served.

If the team considers your contribution to be major, you may be eligible for the Major Contributor badge on Retro WFC, the Developer rank on Discord, a mention on our website and explicit feature credit on RR's Wiiki page. This cannot be requested and instead will be given out at the team's discretion.

## Special requests

If there's any condition or request that has to be accommodated for your contribution not covered by these guidelines, please reach out to the team before making your full contribution. We usually don't accommodate special requests.

We expect contributors to have read our guidelines, so requests in code contributions will be considered soft-asks and not showstoppers.
